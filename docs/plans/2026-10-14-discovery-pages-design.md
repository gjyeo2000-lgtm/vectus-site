# 벡투스 고객 질문별 공개 안내 페이지 설계도 (구현 전 검토안)

작성일: 2026-10-14. 대상: `vectuslab.com` 회사 홈페이지. 이 문서는 설계와 목업만 다루며, 운영 페이지나 추천 엔진을 변경하지 않는다.

## 1. 목적과 전제

- 현재 홈페이지는 투자·보험·기술·비전을 한 페이지에 설명한다. 고객이 “주식 판단의 근거는?”, “내 ETF 안에 무엇이 겹치나?”, “보유보험 진단은 어디까지 가능한가?”를 각각 묻는다면 답을 찾기 위해 긴 페이지를 탐색해야 한다.
- 목표는 AI에 추천을 강제하는 것이 아니라, 고객 질문에 대한 **독립적이고 검증 가능한 공개 답변**을 제공하는 것이다. 브랜드명 없이 묻는 추천 질문에서 발견될 가능성은 결과이지 보장 목표가 아니다.
- 정식 공개 홈페이지와 초대자 전용 테스트 웹을 구분한다. 준비 중인 기능을 현재 제공으로 표시하지 않는다. 금융 판단·보험금 지급·절감액·AI 추천 노출을 보장하지 않는다.
- 기존 홈페이지의 히어로 연결 그래프, 판단 과정, 관계 그래프, 시간축, 보험 장면과 일반 모션은 삭제하거나 대체하지 않는다.

## 2. 정보 구조

| 공개 주소 초안 | 고객 질문 | 페이지의 핵심 답 | 서비스 단계 |
| --- | --- | --- | --- |
| `/stock/` / `/en/stock/` | “종목 판단은 무엇을 근거로 하나요?” | 원천·기준일·지표의 적용 범위·판단/보류 사유를 확인한다. 개별 종목의 수익이나 매매 시점을 확정하지 않는다. | 초대 테스트 범위 확인 |
| `/fund-etf/` / `/en/fund-etf/` | “내 펀드·ETF 안에 같은 위험이 겹치나요?” | 지원되는 상품 구성과 고객이 등록한 보유상품을 연결해 노출·중복을 살펴본다. 직접 등록한 범위 밖의 보유자산을 아는 척하지 않는다. | 초대 테스트 범위 확인 |
| `/insurance/` / `/en/insurance/` | “내 약관에서 중요한 특약·청구 조건은 무엇인가요?” | 보유계약과 확인된 공식 약관·상품판을 맞추어 중요한 조건을 설명한다. 실손의료보험부터 범위를 넓히며 개인별 보험료 견적·보험금 지급을 확정하지 않는다. | 범위 확대 중 |

- 현행 `/`와 `/en/`는 회사·서비스 종합 소개로 유지한다. 히어로와 기존 그래프는 그대로 두고, `service-status` 뒤에 “무엇을 확인하고 싶으신가요?” 진입 카드 3개를 더하는 안을 목업에서 보여준다.
- 하위 페이지에서 홈으로 돌아갈 수 있게 하고, 한·영 대응 주소를 서로 연결한다. 새 주소는 **구현·검증·공개 후에만** 사이트맵에 넣는다. 목업 주소는 사이트맵에 넣지 않는다.
- `/insurance/`는 현재 홈의 보험 소개를 복제해 경쟁하는 페이지가 아니다. 고객 질문·확인 순서·제외 범위를 요약하고 상세 설명은 기존 홈 보험 구역과 연결한다.

## 3. 화면·문구 계약

공통 화면은 ① 고객 질문과 답 한 문장 ② 현재 제공 단계 ③ 근거를 확인하는 순서 ④ 가능/보류/미지원의 구분 ⑤ 다음 탐색 링크 순이다. 목업의 관계선과 상태 카드는 설명용이며 실제 시세·상품·고객 결과를 표시하지 않는다.

| 화면 | 상단 문구 초안 | 보류·범위 문구 |
| --- | --- | --- |
| 주식 | “종목 이름보다 먼저, 판단의 기준일과 근거를 봅니다.” | “필요한 시세·공시·관측이 부족하면 결론 대신 이유를 표시합니다.” |
| 펀드·ETF | “상품이 달라도 같은 종목의 위험은 겹칠 수 있습니다.” | “등록한 보유상품과 확인된 구성 정보에 한해 연결합니다.” |
| 보험 | “보험을 더 팔기보다, 고객이 받을 보장의 조건을 먼저 봅니다.” | “연결된 보유계약과 확인된 공식 약관·상품판에 한해 설명하며, 지급·절감액은 보장하지 않습니다.” |

주식 페이지는 “상승 확률”, “보장 수익” 같은 검증되지 않은 결과를 예시로 쓰지 않는다. 펀드·ETF 페이지는 그림 속 두 상품을 실제 고객 보유나 실시간 구성으로 읽히지 않게 표시한다. 보험 페이지는 설계사를 폄하하지 않고 반복 약관 대조 시간을 줄이는 **목표**를 설명한다.

## 4. 구현 단계 (목업 승인 후)

1. 각 공개 페이지의 한국어·영어 문구와 제공 단계에 대해 제품 담당자가 실제 테스트 웹/API와 대조한다. 다르면 문구를 먼저 고친다.
2. 기존 홈페이지의 색·타이포그래피·네비게이션·모션 규칙을 재사용한다. 모바일, 키보드 접근, `prefers-reduced-motion`을 동일하게 지원한다.
3. 정적 HTML 페이지를 한·영 쌍으로 만들고 홈 진입 카드, 하위 페이지 교차 링크, canonical, hreflang, 내부 링크를 연결한다. 구조화 데이터는 화면에 보이는 사실만 기재한다.
4. 브라우저에서 320/390/768/1440px, 한·영, 링크·접근성·가로 넘침·콘솔 오류·모션 축소·스크린샷을 점검한다. 기존 홈페이지 그래프와 문구가 남아 있는지 회귀 검사한다.
5. 공개 배포 뒤 실제 응답과 사이트맵을 확인하고 Search Console에서 색인 상태를 점검한다. AI 답변은 동일 질문·검색 모드·날짜·인용 URL을 기록해 비교하되 추천 여부를 출시 판정으로 사용하지 않는다.

## 5. 검토·수용 기준

- 고객은 홈에서 3개 질문을 보고 1회 클릭으로 해당 설명에 도달한다.
- 각 페이지 첫 화면에서 “무엇을 확인할 수 있는지”, “지금 가능한 범위”, “무엇을 단정하지 않는지”를 구별할 수 있다.
- 한·영 설명의 의미와 서비스 단계가 일치한다. 예시 그래프는 실제 고객 결과로 오해되지 않는다.
- 기존 홈의 역동적 그래프와 보험·투자 소개는 유지한다. 새 페이지는 SEO용 빈 문구가 아니라 고객에게 독립적인 답을 준다.
- 구현·배포·검색 반영은 별개로 보고한다. 이 설계와 목업만으로 실제 페이지가 출시되거나 Gemini/ChatGPT 추천이 보장되지 않는다.
